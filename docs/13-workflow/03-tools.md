# 13-3 執筆に使えるツール一覧

第6-6節で、Search Console と Analytics は診断機セットであると述べました。執筆現場も同じです。ツールを増やすほど段取り表から目が離れ、更新されないダッシュボードが増えます。本章では、5ステップごとに「これだけあれば回る」最小セットを示します。

## ツール選定の原則

> この節の要点：ツールは段取りを支える道具である。工程に合う道具を選び、最小セットを決め、導入を増やしすぎない。

| 原則 | 内容 |
|---|---|
| 段取り優先 | ツールに合わせて工程を変えない。工程に合う道具を選ぶ |
| 最小セット | 新規導入は月1回まで。既存ツールの活用を先に |
| 共有形式 | 企画シート・アウトラインは全員が同じテンプレート |
| 記録 | 改善前後はスプレッドシート1枚に集約（第6章） |
| 出口 | 公開後の計測は第6章・第14章のセットに接続 |

無料ツールだけでも、本章のワークフローは成立します。有料ツールは、ボトルネックが特定できてから導入します。

---

## ステップ1：企画

> この節の要点：企画段階はスプレッドシートとカレンダーで十分。テンプレートを固定し、Must・成功指標・承認者欄を標準化する。

| 用途 | ツール例 | 備考 |
|---|---|---|
| 企画シート | スプレッドシート、Notion、Google ドキュメント | テンプレート固定 |
| カレンダー | Google カレンダー、Asana、Backlog | 第12章の公開日と同期 |
| 優先度 | スプレッドシート | Impact × Urgency ÷ Effort（第6-5節） |

企画シートは、リポジトリ内の [article-outline テンプレート](../../templates/article-outline.md) をベースに、Must・成功指標・承認者欄を足した形式が扱いやすいです。

---

## ステップ2：リサーチ

> この節の要点：リサーチ結果はURLと取得日で残す。チャットやPDFだけでは、後から証明書として検証できない。

| 用途 | ツール例 | 備考 |
|---|---|---|
| 検索意図の確認 | ブラウザのシークレット検索、上位記事の手動読解 | 第2-1節 |
| キーワード補助 | Google キーワードプランナー、Ubersuggest 等 | 補助。主役は問い |
| 自社データ | Search Console | 既存サイトがある場合 |
| 出典管理 | スプレッドシート、ブックマークフォルダ | URL・取得日・引用箇所 |
| 競合メモ | ドキュメント | H2一覧・足りない角度 |
| AI補助 | ChatGPT、Gemini 等 | 平易語チェック・構成案の壁打ち（最終判断は人間） |

リサーチ結果は、執筆者以外も読めるよう、箇条書きとURLで残します。PDFだけ保存すると、後から検証できません。

---

## ステップ3：構成

> この節の要点：アウトライン段階でtitle・meta・H1の案を1行ずつ書いておく。執筆後の外門修正を減らす。

| 用途 | ツール例 | 備考 |
|---|---|---|
| アウトライン | ドキュメント、Markdown、CMSの下書き | H2＋PREPメモ |
| 見出し検証 | 音声読み上げ、見出しだけコピーした一覧 | 第3-2節 |
| ワイヤー | Figma、紙、ホワイトボード | ファーストビュー確認（第9章） |

アウトライン段階で、title・meta・H1の案を1行ずつ書いておくと、執筆後の外門修正が減ります（第5-3節）。

---

## ステップ4：執筆

> この節の要点：変更履歴が残る執筆環境を固定する。共同編集はH2単位で担当を分け、衝突を防ぐ。

| 用途 | ツール例 | 備考 |
|---|---|---|
| 本文執筆 | Google ドキュメント、Notion、CMS | 変更履歴が残るもの |
| トーン参照 | ブランドガイドライン（第8-4節） | 語彙NG・良い例 |
| 語数・可読性 | 文字数カウンタ | リード50〜150字の目安（第4-3節） |
| 画像 | 圧縮ツール、スクリーンショット | 第9-5節の軽量化 |
| CMS | WordPress、microCMS、Contentful 等 | プレビューURLをレビューに使う |

執筆中にリアルタイム共同編集する場合、H2単位で担当を分けると衝突が減ります。共同編集は校正ステップより執筆ステップ向きです。

---

## ステップ5：校正

> この節の要点：校正ツールは指摘を全部直すのではなく、レイヤーごとに分類して直す。CMSプレビューと実機で構造を確認する。

| 用途 | ツール例 | 備考 |
|---|---|---|
| 誤字・表記 | テキストエディタの校閲、LanguageTool 等 | です・ます統一 |
| 構造確認 | CMSプレビュー、モバイル実機 | 第9章 |
| alt・リンク | ブラウザ開発者ツール、WAVE 等 | 第10章 |
| チェックリスト | 13-1節、第7-4節 | 印刷して手元で確認可 |
| 差分管理 | ドキュメントの変更履歴、Git | リライト時に特に有効 |

校正ツールは「指摘を全部直す」ではなく、レイヤー（外門・関所・証明書）ごとに分類して直します（13-4節）。

---

## 公開・運用

> この節の要点：公開後はSearch Console＋GA4＋スプレッドシートに集約する。公開日+28日の再試運転をカレンダーに記事名まで書き込む。

| 用途 | ツール例 | 備考 |
|---|---|---|
| 公開 | CMS、ステージング環境 | 本番前プレビュー必須 |
| インデックス確認 | Search Console URL検査 | 重要記事・URL変更時 |
| 行動分析 | Google Analytics（GA4） | 第6章、第14章 |
| 改善記録 | スプレッドシート | 第6-6節の改善ログ |
| リライト管理 | タスクボード、カレンダー | 第11章 |

公開後28日目の再試運転は、カレンダーに「記事タイトル・指標名」まで書き込みます。リマインダーのみだと、何を見るか忘れます。

---

## 避けたいツール導入パターン

> この節の要点：全工程を1ツールに寄せたり、ダッシュボードだけ増やしたりしない。工程ごとの最小セットに逆マッピングする。

| パターン | 問題 | 改善の方向 |
|---|---|---|
| 全工程を1ツールに寄せる | 企画と計測が混ざる | 工程ごとに最小セット |
| 執筆前にSEOツールだけ入れる | 問いよりKWが主役になる | 第2章の問いを先に。AIは補助に留める |
| ダッシュボードだけ増やす | 見る人がいない | 月次60分ルーティン（第6章） |
| 外注にCMSだけ渡す | 構造・altが崩れる | 入稿は内製またはチェックリスト |

---

## 推奨：チーム最小構成

> この節の要点：企画・構成・執筆・校正・運用の4カテゴリが揃えば、第8章〜第12章を含むワークフローが回る。追加ツールはボトルネックが文書化されてから。

| カテゴリ | 推奨 | 人数 |
|---|---|---|
| 企画・構成 | スプレッドシート + ドキュメント | 全員 |
| 執筆 | CMS + ガイドライン | ライター |
| 校正 | チェックリスト + プレビュー | 編集者 |
| 運用 | Search Console + GA4 + スプレッドシート | ディレクターまたはライター |

この4点が揃えば、第8章〜第12章の知見を含むワークフローが回ります。追加ツールは、ボトルネック（レビュー遅延、出典管理の混乱など）が文書化されてから検討します。

---

### ポイント

- 工程ごとの最小セットを決め、乱立を防ぐ
- 企画シート・アウトライン・改善ログは同じ形式で共有
- 執筆ツールより、段取り表とチェックリストが品質を決める
- 公開後は Search Console + GA4 + スプレッドシートに集約

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| ツール導入が目的化 | 段取りが更新されない | 5ステップに逆マッピング |
| 出典をチャットのみ | 証明書が検証不能 | URLリストをスプレッドシート化 |
| プレビュー省略 | モバイルで崩れる | 校正で実機確認 |
