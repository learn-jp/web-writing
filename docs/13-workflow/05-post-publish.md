# 13-5 公開後の運用フロー

第7-6節で、出荷して終わりにしないと述べました。公開後に反応が薄くて落ち込んだ経験があっても、それは最初の一週間では判断できません。第13章の5ステップは公開ボタンで一区切りですが、ワークフロー全体としては公開後の運用まで含めて初めて「1周」です。整備工房でいえば、納車後の定期点検と同じ位置づけです。第6章の精密検査と第5章 Web最適化の外門を、28日後に改めて確かめましょう。

## 公開直後（Day 0〜7）

> この節の要点：公開は第2の返球の開始点である。Day 0〜7は数値判断ではなく、届く準備の週として確認・リンク・記録を行う。

| 作業 | 担当 | 内容 | 参照 |
|---|---|---|---|
| 公開確認 | 編集者 | 本番URL、表示崩れ、リンク切れ | 13-1節 |
| インデックス | 技術またはライター | Search Console URL検査（重要記事） | 第5章 Web最適化 |
| 内部リンク | ライター | 既存記事から新記事へリンク追加 | 第5-5節 |
| SNS・メール | ディレクター | 告知文は外門（title）と整合。OGP・要約文も確認 | 第12章 |
| AI引用確認 | ライター | 主要クエリでGemini・ChatGPTに質問し、引用・要約の正確性を spot check | 第5章・第10章 |
| 記録 | ライター | 改善ログに1行（公開日・想定KPI） | 第6-6節 |

公開直後に数値を判断しないでください。表示・クリックは数日〜数週で安定します。Day 0〜7は「届く準備」の週です。

### Day 0 チェックリスト

- [ ] 本番URLが意図どおり
- [ ] title・meta・H1がプレビューと一致
- [ ] 証明書欄（更新日・出典）が表示されている
- [ ] スマホ・PCでファーストビューを確認
- [ ] 改善ログスプレッドシートに行を追加
- [ ] カレンダーに「公開日+28日 再試運転」を登録
- [ ] SNS告知文・OGPが外門と整合している

## 再試運転（Day 28）

> この節の要点：公開から28日後に第6章の第2の返球を確認する。新規記事でも必須。判定に応じて部分リライトまたは全面リライトへ接続する。

第6章の第2の返球を、新規記事でも必ず確認します。リライト（第11章）と同型です。

| 指標 | 見る目的 | 参照 |
|---|---|---|
| 表示回数 | 物流（インデックス・順位） | 第6-3節 |
| 外門の通過 | 外門（title・meta） | 第6-2節 |
| 一ページだけ見て去る割合 | 防波堤（リード）・意図 | 第6-2節 |
| 主要クエリ | 問い×答え適合 | 第6-4節 |
| 読み続け・スクロール | 関所 | 第6-3節 |

| 判定 | 次のアクション |
|---|---|
| すべて想定内 | 月次精密検査の通常監視へ |
| 外門のみ弱い | 部分リライト（title・meta） | 第11章 |
| 防波堤・関所 | 部分リライト（リード・H2） | 第11章 |
| 複数レイヤー | 全面リライトを計画 | 第11-1節 |
| カニバリ疑い | 統合・役割分担 | 第11-4節 |

28日時点のスナップショットを、改善ログに「改善前」として残します。後からリライトしたとき、前後比較ができます。

## 月次運用（第6章ルーティン）

> この節の要点：公開後の記事を第6-6節の月次60分ルーティンに組み込む。新規制作と既存改善の工数配分をディレクターが月単位で決める。

公開後の記事は、第6-6節の月次60分ルーティンに組み込みます。

```
月初 10分 … 全体の表示・外門の通過変動
    ↓
記事別 30分 … 重点3本（新規記事は公開後2ヶ月目から候補に入りやすい）
    ↓
記録 10分 … 改善ログ更新
    ↓
前月確認 10分 … リライト記事の効果
```

第12章のコンテンツカレンダーと並走させます。新規制作（13-1節）と既存改善（第11章）の工数配分を、ディレクターが月単位で決めます。

> この節の要点：月次に加え、四半期でハブリンク・鮮度・カニバリを見直す。年1回はワークフロー自体も更新する。

| 周期 | 作業 | 参照 |
|---|---|---|
| 四半期 | ハブ記事の内部リンク見直し | 第5-5節 |
| 四半期 | 2年以上未更新×表示多のリスト | 第11-3節 |
| 四半期 | カニバリ診断 | 第11-4節 |
| 年次 | ガイドライン・ワークフロー自体の見直し | 第8-4節、本章 |

ワークフロー（段取り表）も固定しすぎると、CMS変更やチーム体制変更に追随できません。年1回、13-1節のチェックリストとRACIを更新します。

> この節の要点：第8章〜第12章は公開後にも効く。新規記事1本は制作と運用の両方を通過して初めて資産になる。

新規記事1本は、制作ワークフロー（13-1節）と運用ワークフロー（本节）の両方を通過して、初めて「資産」になります。

## 公開後フロー全体図

> この節の要点：制作5ステップの先に、Day 0・Day 28・月次の3リズムが続く。異常時は第11章のリライトフローへ分岐する。

```
【制作】企画 → リサーチ → 構成 → 執筆 → 校正 → 公開
                                              ↓

                                              ↓
【運用 Day 28】   再試運転（第6章）
                                              ↓
         ┌────────────────────────────────────┐
         │  OK → 月次精密検査（第6章）          │
         │  NG → リライト（第11章）→ 証明書更新 │
         └────────────────────────────────────┘
                                              ↓
【月次・四半期】  カレンダー・鮮度・カニバリ（第11章・第12章）
```

## 改善ログの列（公開後用）

> この節の要点：公開後の数値と判定を改善ログ1枚に集約する。制作とリライトを同じ表で管理し、工数配分を決めやすくする。

| 列 | 例 |
|---|---|
| 記事URL | /blog/side-job-start/ |
| 公開日 | 2026-06-01 |
| 想定KPI | 外門通過 1.5% |
| Day28 外門通過 | 1.2% |
| Day28 玄関で引き返す | 68% |
| 判定 | 外門弱い |
| 次アクション | title部分リライト |
| 担当 | ライターA |
| 完了日 | 2026-07-10 |

ログが1枚に集まると、ディレクターが月次で「制作 vs リライト」の工数を決めやすくなります。

---

### ポイント

- 公開は第2の返球の開始。Day 0・Day 28・月次の3リズム
- Day 28の再試運転は新規記事でも必須
- 異常時は第11章のリライトフローへ接続
- 改善ログ1枚で制作と運用をつなぐ

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| 公開後すぐに数値判断 | 誤った全面リライト | 28日待つ |
| 再試運転未設定 | 改善効果が不明 | 公開日+28日をカレンダー固定 |
| 新規だけ作る | 既存資産が眠る | 月次3本リライト（第11章） |
| ログが散在 | チームで同じ判断ができない | スプレッドシート1枚 |
