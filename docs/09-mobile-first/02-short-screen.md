# 9-2 短い画面で伝える構成テクニック

通勤電車で記事を開いて、スクロールする前に「長い」と感じて閉じた経験はありませんか。狭い画面でも最後まで辿り着ける構成は、努力の問題ではなく設計の問題です。自分がスマホで検索結果をタップしたときも、SNSのプレビューから来たときも、本文に入った瞬間の画面は同じく狭い。第5章 Web最適化で整えた外門を通過したあと、ここから先も返球を続けましょう。

## 第3章の導管を、狭い画面向けに再調整する

> この節の要点：PREP法・見出し階層・段落ルールを、「1画面に何行見えるか」という物理制約で再計算する。スマホほど、スキャンして見出しで飛び、合わなければスクロールせず戻る。

第3章（[情報設計と構成](../03-structure/)）で、PREP法・見出し階層・段落ルールを学びました。モバイルファーストでは、その設計を「1画面に何行見えるか」という物理制約で再計算します。

第2章（[2-3 読者の読み方](../02-reader-media/03-reading-behavior.md)）で述べたスキャン・ジャンプ・引き返しは、スマホほど早く起きます。自分も全文は読まず、見出しで関所を飛び、必要な段落だけ深く読む。狭い画面では、その判断が一瞬で終わります。

狭い画面向けの導管設計は、この読み方を前提に、関所の密度と段落の長さを調整することです。

---

## 1画面単位で考える段落設計

> この節の要点：PCでは10行見える段落も、スマホでは15行以上に膨らんで見える。1段落3〜4文、スマホで5〜8行以内を目安に、1段落1主題をより厳密に守る。

### 目安：1段落＝3〜4文、スマホで5〜8行以内

PCでは10行以上見える段落も、スマホでは15行以上に膨らんで見えます。自動車整備士が狭いピットでは大きな工具を使わず、手の届く範囲の工具だけを並べるように、1段落に載せる情報量を絞ります。

```
❌ スマホで読みにくい段落
  前置き2文 → 本論3文 → 補足2文 → まとめ1文（計8文、1画面超）

✅ スマホ向けの分割
  段落A：前置き＋本論の核（3文）
  見出しまたは空行
  段落B：補足（3文）
  段落C：まとめ（2文）
```

第3章の「1段落1主題」を、モバイルではより厳密に適用します。1段落に二つの論点が入っていると、スマホでは「どこまでが一つの話か」が見えにくくなります。

### 改行と空行は「呼吸」

寿司職人が握りと握りの間に少し間を置くように、段落間の空行は、スマホで読む自分の目と指の休息になります。詰め込みすぎた導管は、狭い画面では圧迫感として返ってきます。

---

## 見出しを「1画面1関所」に近づける

> この節の要点：H2間300〜500字を目安に、見出しだけ流し読みした自分が次の関所まで辿り着ける密度にする。見出しは15〜25字程度、単独で意味が通じる文言に。

### H2の間隔：300〜500字を目安に

スマホでH2から次のH2までが長すぎると、見出しだけ流し読みした自分は「まだ同じ関所にいる」と感じ、スクロールせず戻りやすくなります。

| 要素 | PC向けの感覚 | モバイル向けの目安 |
|---|---|---|
| H2間の文字数 | 800字以上もあり得る | 300〜500字程度で次のH2 |
| H3の役割 | 細分化 | スキャン時の「小さな関所」 |
| 見出しの文言 | やや長くても可 | 15〜25字程度、単独で意味が通じる |

第3章（[2-2 見出し階層の設計](../03-structure/02-heading-hierarchy.md)）のH2は「スクリーニングゲート」でした。スマホでは、ゲートとゲートの距離が長いと、次の関所まで辿り着かずに消滅します。

もしあなたが、見出しだけをスマホで上から流し読みして、記事の全体像が掴めるか試していないなら、公開前の必須確認です。

## リストと表のモバイル向け置き換え

> この節の要点：横に5列以上の表はスマホで横スクロールが必要になり、読み飛ばされる。表はリスト化し、本文で要点を言い換えて補足する。

### 横長の表は、スマホでは「リスト化」を検討

第2章のデバイスチェックリストにもあった通り、横に5列以上の表は、スマホで横スクロールが必要になり、自分なら読み飛ばして本文の答えに辿り着かない場面が増えます。

```
表（PC向け）          →  リスト（モバイル向け）
| 項目 | A | B | C |     ・項目A：説明
                       ・項目B：説明
                       ・項目C：説明
```

表が必要な場合は、本文で要点を言い換えて補足します。「表を見てください」だけにしない。寿司職人が献立表だけ渡して握りを出さないように、本文が単体で答えになる設計です。

### 番号付きリストは「実行中」に読まれる

第2章で触れた通り、手順記事（Do意図）はスマホで見ながら実行されることが多いです。ステップは1項目1アクション、各項目2〜3文以内に抑えます。

---

## 逆ピラミッドを、画面の縦軸に重ねる

> この節の要点：画面上部に答えの核がないと、自分はスクロールする前に戻る。逆ピラミッドを縦方向の情報の重さとして設計し、ファーストビューとセットで適用する。

第3章の結論ファースト（逆ピラミッド）は、モバイルでは縦方向の「情報の重さ」にも直結します。

```
画面上部（軽い・答えの予告）
    ↓
中盤（根拠・手順）
    ↓
下部（補足・関連リンク）
```

自分がスクロールするほど、時間を投資しています。上部に答えの核がないと、投資する前に戻ります。第4章（[4-4 結論ファーストの実践](../04-headlines-leads/04-conclusion-first.md)）の技法を、ファーストビュー（第9-3節）とセットで適用してください。

## 執筆中のスマホプレビュー習慣

> この節の要点：執筆中に定期的にスマホプレビューを挟む習慣が、モバイルファーストの核心。PCの大画面だけで「完成」と判断しない。

整備士が作業後に最小ピットで動作確認するように、執筆中に定期的にスマホプレビューを挟む習慣が、モバイルファーストの核心です。

```
□ アウトライン段階：H2だけをスマホで流し読み
□ 初稿完成：各H2間の文字数を確認
□ 公開前：段落・表・CTAをスマホでタップ確認
```

PCの大画面だけで「完成」と判断しない。第6章の精密検査以前に、第1の返球の段階で封筒サイズを確かめる礼儀です。

---

### ポイント

- 第3章の導管を、1画面に見える行数で再計算する
- 段落3〜4文、H2間300〜500字を目安に
- 横長の表はリスト化または本文で要点を補足
- 執筆中からスマホプレビューを挟む

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| PC基準の段落長のまま | 1画面超の塊に見える | 段落を分割、1段落1主題 |
| H2が800字以上空く | 流し読みで迷子 | H3で中間関所を設ける |
| 表だけで情報を伝える | スマホで読めない | リスト化＋本文で言い換え |
| 初稿のみPC確認 | 構造が後から直せない | 執筆中にスマホプレビュー |
