# 10-5 読み上げを意識した文章構造

スクリーンリーダーは、画面を「上から順に」ではなく「構造の印」を頼りに読む。第3章の見出し階層と、第10章の平易語・altが揃って初めて、音声でも答えに辿り着ける導管になる。

## スクリーンリーダーが読むもの

> この節の要点：スクリーンリーダーは見出し・段落・リンク・リスト・画像（alt）・表を読み上げる。視覚的なレイアウトは読まれず、第3章の論理の骨格が音声の地図になる。

スクリーンリーダー（NVDA、JAWS、VoiceOver、TalkBackなど）は、主に次を読み上げます。

| 要素 | 読み上げの例 |
|---|---|
| 見出し | 「見出しレベル2、始める前に就業規則を確認する」 |
| 段落 | 本文テキスト |
| リンク | 「リンク、副業届出書PDF」 |
| リスト | 「リスト、3項目。1、就業規則を確認…」 |
| 画像 | altの内容（空ならスキップまたはファイル名） |
| 表 | セルと行・列の見出し |

視覚的な「レイアウト」（右寄せ、2カラム、色のブロック）は、基本的に読まれません。第3章で学んだ「論理の骨格」こそが、音声の地図です。

> スクリーンリーダーにとって、見出し階層は目次そのものである。H2を飛ばしてH3だけ並べる設計は、地図の中抜けと同じ。

## 第3章との接続：見出しは音声の標識

> この節の要点：スクリーンリーダー利用者は見出し一覧で骨格を把握し、目的のH2までジャンプする。H2を飛ばす階層は、音声でも地図の欠落になる。

第3章で、見出しは「関所」「標識」と述べました。スクリーンリーダー利用者は、次の操作をします。

1. 見出し一覧で記事の骨格を把握（H2だけジャンプ）
2. 目的のH2まで移動
3. そのセクションを段落単位で読む

階層が乱れると、音声でも「どの工程の下位か」がわかりません。

```html
<!-- 悪い例：H2を飛ばす -->
<h1>副業の始め方</h1>
<h3>就業規則の確認</h3>
<h3>クラウドソーシング</h3>
```

「ブラウザでの表示結果（見た目）」：

- ブラウザは見出しのサイズ差で表示するため、一見問題なく見える場合がある
- スクリーンリーダーは「レベル1の次がレベル3」と報告し、階層の欠落を示す
- 見出しナビゲーションで「レベル2がない」ため、スキップの粒度が崩れる

```html
<!-- 良い例：第3章の階層 -->
<h1>副業の始め方（初心者向け）</h1>
<p>結論：最初の一歩は就業規則の確認です。</p>
<h2>始める前に就業規則を確認する</h2>
<p>社内ポータルまたは総務に問い合わせてください。</p>
<h2>在宅で試せる副業の種類</h2>
<h3>クラウドソーシングのライティング</h3>
<p>週末2時間から始められます。</p>
```

「ブラウザでの表示結果（見た目）」：

- H1→H2→H3のサイズ差で、視覚読者も骨格が掴める
- スクリーンリーダーは見出しレベル2が2つ、レベル3が1つ、と正確に目次を構築
- 第2章のジャンプ読みと、音声のジャンプ読みが、同じ構造で支援される

自動車整備士が配線図の階層を追うように、音声ユーザーは見出しの印を追います。

## リンク・略語・読み上げにくい表記

> この節の要点：リンク文言は目的地を明示し、略語は初出で展開し、長いURLは意味のあるリンクテキストに、記号は文脈で説明を添える。

### リンク文言

```
✗ 「詳細は<a href="/rules">こちら</a>」
✓ 「<a href="/rules">就業規則の確認手順</a>を見てください」
```

リンク一覧機能では、「こちら」が並び、先に進めません。

### 略語の初出

```
✓ 初出：「Web最適化（検索・SNS・AI引用）」
✓ 2回目以降はSEOのみ
```

読み上げソフトは略語を1文字ずつ読むことがあります。初出で展開を書いておくと、理解と音声の両方に効きます。

### URLの扱い

本文中に長いURLを羅列せず、リンク文言に意味を持たせます。

```html
<p>届出書は
   <a href="https://example.com/forms/long-url-here.pdf">副業届出書（PDF）</a>
   から取得できます。</p>
```

### 記号の読み上げ

「※」「→」「★」は、文脈で説明を添えます。

```
✓ 「注意（※）：届出が必要な場合があります」
✗ 「※のみで注意を示す」
```

## リストと表：音声での「段取り」

> この節の要点：番号付きリストはスクリーンリーダーにとって「番号付きの作業手順」。手順を長い段落に書くより、ジャンプと再確認がしやすい。

第3章のリスト・表は、スクリーンリーダーにとって「番号付きの作業手順」です。

```html
<h2>今週末までにやること</h2>
<ol>
  <li>就業規則を確認する</li>
  <li>副業の種類を1つ選ぶ</li>
  <li>クラウドソーシングに登録する</li>
</ol>
```

「ブラウザでの表示結果（見た目）」：

- 1. 2. 3. と番号付きで縦に並ぶ
- スクリーンリーダーは「番号付きリスト、3項目」と読み、各項目を順に読み上げる
- 段落に手順を書くより、ジャンプと再確認がしやすい

寿司職人が「一貫目、二貫目」と順序を伝えるように、番号付きリストは音声の段取りです。

## 読み上げテスト：執筆後の5分チェック

> この節の要点：VoiceOverや音声読み上げで記事を聴き、見出し・リンク・alt・文の長さ・結論への到達を確認する。耳での精密検査。

公開前に、次のいずれかを試してください。

1. macOS/iOSのVoiceOver、Windowsのナレーターで記事を開く
2. 記事をコピーし、音声読み上げ機能（ブラウザ拡張、OS標準）で聴く
3. 同僚に目を閉じて読んでもらい、どこで迷うかメモしてもらう

確認ポイント：

- [ ] 見出しだけ聴いて、記事の流れがわかるか（第3章）
- [ ] リンク文言だけで、次に何が起きるかわかるか
- [ ] 画像のaltで、図の要点が足りるか（10-3節）
- [ ] 1文が長すぎず、息継ぎの位置が自然か（10-2節）
- [ ] 結論（答え）に、音声だけでも辿り着けるか

第6章の精密検査は数字でした。ここでは「耳での精密検査」です。どちらも、第2の返球を読む設計士の仕事です。

## 3つの読み手：スクリーンリーダー・検索・AI

> この節の要点：スクリーンリーダー、検索インデックス、AI引用は、同じHTML構造の「印」を頼りに読む。三人の受け取り手への同時の返球。

第1章で、Webライティングには「二人の受け取り手」があると述べました。第10章では、実際には三つ目の読み手（Gemini・ChatGPTなどのAI）：も加わります。いずれも、HTMLの見出し・リスト・表構造を解析します（第3章・第5章 Web最適化（検索・SNS・AI引用））。

| 構造 | 視覚読者 | 音声読者（スクリーンリーダー） | 検索・AI引用 |
|---|---|---|---|
| H1→H2→H3 | スキャン | 目次ジャンプ | 論理マッピング・要約の骨格 |
| 意味のあるalt | 画像理解 | 図の内容 | 画像の文脈理解 |
| 表のth | 表の読み取り | セルと見出しの対応 | 表データの解釈 |
| 平易な冒頭 | 冒頭の判断 | 結論への早期到達 | 引用スニペットの候補 |

「小手先の最適化」ではなく、正当性を証明するエンジニアリング（第3章・第7章）の延長です。構造を正しく設計することは、人間の読者に届ける第一目的であり、検索・AI引用はその結果として機能します。

## 消滅を音声側でも防ぐ

> この節の要点：音声で読む自分が途中で戻る理由は、視覚で読む自分と同型。見出し・リンク・専門用語・結論の遅さ（第4章の結論ファーストが音声側の防波堤になる。）

音声で読む自分が途中で戻る理由は、視覚で読む自分と同型です。

- 見出しが標識として機能せず、目的の答えが見つからない
- リンクが「こちら」ばかりで、次の行動が決められない
- 専門用語の壁（第7章）で「自分向けではない」
- 結論が遅く、長い前置きだけが読み上げられる

第4章の結論ファーストは、音声で読む自分にとっても「出口の予告」です。リードで結論を述べ、H2冒頭でもP（要点）を置く。それが、戻る前に答えに辿り着ける、音声側の防波堤です。

---

### ポイント

- スクリーンリーダーは構造（見出し・リスト・表・alt）を頼りに読む。AI引用も同じ印を要約の骨格にする
- 第3章の見出し階層は、音声の目次。飛ばし・乱れは地図の欠落
- リンク・略語・記号は、音声だけでも意味が通じるように
- 読み上げテストは、公開前の5分投資

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| divで見出し風に装飾 | 見出しとして読まれない | h1〜h4を使う（第3章） |
| リンク「こちら」連発 | リンク一覧が無意味 | 目的地を文言に |
| 長いURLをそのまま掲載 | 読み上げが冗長 | 意味のあるリンクテキスト |
| 音声テスト未実施 | 気づかない欠落 | VoiceOver等で1回確認 |
