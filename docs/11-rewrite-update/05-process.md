# 11-5 リライトの手順とチェックポイント

リライトを「なんとなく直す」作業にすると、改善前後の比較ができず、同じ故障を繰り返します。整備現場と同様、診断→計画→執筆→証明書更新→再試運転の段取りを固定し、[第6章](../06-data-analytics/)の精密検査と[第7章](../07-trust-eeat/)の証明書を修理工程に組み込みます。

## リライトの7ステップ

> この節の要点：診断→計画→執筆→構造→証明書→公開→再試運転の7段階。執筆から始めず、第6章と第7章を工程に組み込む。

```
1. 診断（第6章）     … 症状・原因レイヤー・リライト種類
2. 計画              … Must/Must Not再確認、変更範囲の確定
3. 執筆              … レイヤー限定 or 全面
4. 構造・物流        … 見出し、内部リンク、title/meta
5. 証明書更新（第7章）… 更新日、出典、訂正記録
6. 公開・インデックス … 再クロール、必要ならSearch ConsoleでURL検査
7. 再試運転（第6章） … 28日後に第2の返球を比較
```

各ステップにチェックポイントがあります。次節以降で詳述します。

---

## ステップ1：診断（第6章の再適用）

> この節の要点：リライト着手前に、第6章の成果物（想定・予兆・原因レイヤー・マトリクス・優先度）を揃える。診断なしの修理は再発する。

リライト着手前に、必ず[第6章](../06-data-analytics/)の成果物を揃えます。

| 成果物 | 用途 |
|---|---|
| 執筆時の想定（問い・ペルソナ・Must） | 第2章形式。ズレの判定基準 |
| 予兆パターン（6-2節） | 症状のラベル |
| 原因レイヤー | 部分 or 全面の判断 |
| 問い×答えマトリクス（6-4節） | 何を足す・直すか |
| 優先度スコア（6-5節） | 今月着手の根拠 |

診断なしのリライトは、原因不明の部品交換と同じです。直ることもありますが、再発します。

---

## ステップ2：計画

> この節の要点：リライト種類・変更レイヤー・工数・成功指標を計画書に固定する。部分リライトでは触らない範囲も明記し、意図しない全面化を防ぐ。

| 項目 | 記入内容 |
|---|---|
| リライト種類 | 部分 / 全面 / 統合 / 分割 |
| 変更レイヤー | 外門 / 防波堤 / 関所 / 物流 / 鮮度 / 証明書 |
| Must変更の有無 | 変える場合は第2章から再設計 |
| 工数見積 | 時間・担当 |
| 成功指標 | 外門通過 1.5%以上、玄関を通過65%以下 等 |

部分リライトでは、触らない範囲も明記します。「H2-3以降は変更しない」が、意図しない全面化を防ぎます。

---

## ステップ3：執筆

> この節の要点：リライト種類に応じた焦点で執筆する。専門用語を足す方向に偏らず、第7-3節の「問いへの応答」を確認する。

リライト種類に応じた執筆の焦点です。

| 種類 | 執筆の焦点 | 参照章 |
|---|---|---|
| 部分（外門） | title・meta・H1 | 第4章、第5-3節 |
| 部分（防波堤） | リード50〜150字 | 第4-3節 |
| 部分（関所） | 特定H2と直下段落 | 第3章 |
| 全面 | アウトラインから | 第3-5節 |
| 統合 | 複数記事のMust統合 | 11-4節 |
| 鮮度L1/L2 | 数値・出典・手順 | 11-3節 |

執筆中も、[第7-3節](../07-trust-eeat/03-expertise-not-jargon.md)の「専門用語より問いへの応答」を確認します。リライトで専門用語を足す方向に偏りがちです。

---

## ステップ4：構造・物流

> この節の要点：公開前に見出し階層・title/meta/H1の整合・内部リンクを確認する。H2追加時は目次・アンカー・リンク更新もセット。

公開前に、第1章〜第5章の構造を再確認します。

```
□ 見出し階層（H1→H2→H3）に飛び級がない
□ title・meta・H1の整合（第5-3節）
□ 内部リンク：ハブ・関連記事への導線（第5-5節）
□ 統合・分割時：301・リンク切れなし
□ 画像alt・表の構造（第10章）
```

リライトでH2を追加した場合、目次・アンカー・内部リンクの更新もセットです。

---

## ステップ5：証明書更新（第7章）

> この節の要点：リライト後に更新日・改訂内容・出典・著者・利益相反を必ず更新する。リライトは証明書の再発行である。

[第7-4節](../07-trust-eeat/04-evidence-and-authority.md)の記載事項を、リライト後に必ず更新します。

```
□ 最終更新日（今日の日付）
□ 改訂内容（何を変えたか1〜2行）
□ 新規出典・訂正した数値の出典
□ 著者・監修者（変更があれば）
□ 利益相反（新規アフィリエイト等）
□ 生成AI補助を使った場合：事実確認済みの旨（第8-4節）
```

[第7-6節](../07-trust-eeat/06-designers-way-of-life.md)の誓い3「更新し続ける」は、ここで実行されます。リライトは、証明書の再発行です。

---

## ステップ6：公開・インデックス

> この節の要点：URL変更なしが通常。統合・URL変更時は301、重要記事はSearch Console URL検査を行う。

| 作業 | 条件 |
|---|---|
| そのまま上書き公開 | URL変更なし（通常） |
| 301リダイレクト | 統合・URL変更時 |
| Search Console URL検査 | 全面リライト・重要記事 |
| サイトマップ再送信 | 大規模変更時 |

URLを変えない限り、インデックスは自然に更新されます。表示の反映には数日〜数週かかることがあります。

---

## ステップ7：再試運転（第6章）

> この節の要点：28日後に改善前後を同じ指標で比較する。効果がなければ診断に戻り、2回連続で効果なしなら全面リライトまたは統合を検討する。

[第6-6節](../06-data-analytics/06-inspection-workflow.md)フェーズ4と同型です。改善前後を同じ指標で比較します。

| 指標 | 改善前 | 改善後（28日） | 判定 |
|---|---|---|---|
| 外門の通過 | 0.9% | 1.6% | 外門改善、効果あり |
| 玄関で引き返す | 72% | 66% | 微改善、次点検でH2-2 |
| 主要クエリ適合 | △ | ○ | 問い×答え改善 |

効果がなければ、原因レイヤーの見直し（診断の再実行）に戻ります。2回連続で効果なしなら、全面リライトまたは統合を検討します。

---

## リライト前後チェックリスト（実務用）

> この節の要点：公開ボタンの直前に、診断・計画・執筆・構造・証明書・公開後の6ブロックを最終確認する。

公開ボタンを押す前の最終確認です。

### 診断・計画

- [ ] 第6章の症状・原因レイヤーを文書化した
- [ ] リライト種類（部分/全面/統合/分割）を決めた
- [ ] 成功指標を1つ以上定義した

### 執筆・構造

- [ ] Mustと変更範囲が計画と一致
- [ ] 触らない範囲を守った（部分の場合）
- [ ] title・meta・H1・見出し階層を確認
- [ ] 内部リンク・301を確認

### 証明書

- [ ] 更新日・改訂内容を記載
- [ ] 出典・数値を検証
- [ ] 誤り訂正があれば改訂内容に明記

### 公開後

- [ ] 改善記録スプレッドシートに1行追加
- [ ] 28日後の再試運転をカレンダー登録

---

## 第6章・第7章との接続図

> この節の要点：第6章（診断）→ 第11章（修理）→ 第7章（証明書）→ 第6章（再試運転）の循環。出荷して終わりにしない。

```
第6章 精密検査
  │  第2の返球 → 予兆 → 原因レイヤー → 優先度
  ↓
第11章 リライト（本章）
  │  診断 → 計画 → 執筆 → 構造 → 証明書 → 再試運転
  ↓
第7章 証明書
     更新日・出典・訂正 … Trustworthinessの継続
  ↓
第6章 再試運転
     改善前後比較 → 次のリライト or 完了
```

出荷して終わりにしない。[第7-6節](../07-trust-eeat/06-designers-way-of-life.md)の「改善の継続」が、第11章で具体化されます。

---

### ポイント

- 7ステップ：診断→計画→執筆→構造→証明書→公開→再試運転
- 第6章の成果物なしに着手しない
- 証明書更新はリライトの必須工程
- 28日後の再試運転で効果を確かめる
- 効果なしは診断に戻る

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| 執筆から始める | 原因不明 | ステップ1を省略しない |
| 更新日だけ変える | 証明書偽装 | 本文とセット更新 |
| 再試運転しない | 効果不明 | カレンダー固定 |
| 部分が全面に膨らむ | 工数超過 | 計画で範囲を固定 |
