# 12-2 トピッククラスターとハブ記事

この2つを統合し、サイト全体のクラスター設計に昇格させます。記事がバラバラに公開されていても、体系を描けば、自分が次の関所へ進めます。整備計画のある整備士が車両の系統ごとに点検項目を決めるように、あなたの物語の「系統」を決める作業です。

## クラスターとは何か

> この節の要点：1テーマ領域をハブ（中心）とスポーク（詳細）のセットでカバーする。リンク構造が「このサイトは体系を持っている」信号になる。

トピッククラスター（Topic Cluster）とは、1つのテーマ領域を、ハブ記事（中心）とスポーク記事（詳細）のセットでカバーする構成です。

```
        [ハブ：副業の始め方 完全ガイド]
           /    |    \
          /     |     \
    [就業規則] [種類] [登録手順] [確定申告]
         ↑      ↑       ↑          ↑
      スポーク  スポーク  スポーク   スポーク
```

| 要素 | 役割 | 整備計画での対応 |
|---|---|---|
| ハブ記事 | テーマ全体の概観、各スポークへの導管 | 車両の総合点検マニュアル |
| スポーク記事 | 特定の問いに深く答える | 系統別の詳細点検 |
| 内部リンク | ハブ↔スポークの双方向通路 | 部品間の接続・依存関係 |

自分が検索結果から辿れば、ハブから次の関所（スポーク）へ自然にジャーニーを進めます。SNSやAI引用から来たときも同じ：内部リンクと見出し構造が、次の返球への導管になります（第5章 Web最適化（検索・SNS・AI引用））。

## ハブ記事の設計基準

> この節の要点：ハブは「薄く広く」ではなく、全体像を示し詳細はスポークへ送る。Must/Should/Could/Won'tで削ぎ落とす。

ハブ記事は「薄く広く」ではなく、「全体像を示し、詳細はスポークへ送る」記事です。[第3-6節](../03-structure/06-prioritization.md)のMust/Should/Could/Won'tを、クラスター全体に適用します。

### ハブにMustで入れるもの

- テーマ領域の全体像（認知段階の読者向け）
- ペルソナの主要な問いへの入口（[第2-2節](../02-reader-media/02-persona.md)）
- 各スポークへの導管（内部リンク）
- 次のジャーニー段階への橋（検討→決定への接続）

### ハブにShouldで入れるもの

- 比較表・選び方の基準
- よくある不安への短い回答（詳細はスポークへ）

### ハブにCould/Won'tで外すもの

- 1スポークで完結する詳細手順（別記事へ）
- ペルソナのMust Notに抵触する網羅（第2章）
- 更新頻度の高い数値・制度（スポークまたは定期更新欄へ）

```
ハブ記事の自己診断
  □ この記事だけ読めば「次に何を調べればいいか」がわかるか
  □ 各H2がスポーク記事へのリンクになっているか
  □ 1記事に複数テーマが混在していないか（混在なら分割検討）
  □ ペルソナのジャーニー段階（認知〜行動）のどこを担うか明確か
```

## スポーク記事の設計基準

> この節の要点：スポークは1記事1問い。ハブへのリンクと次のスポークへの導管を設計し、新規追加前にカニバリチェックを行う。

スポーク記事は、1つの問い（ボール）に、Mustを満たす深い返球を返す記事です。

| 基準 | 内容 |
|---|---|
| 1記事1問い | 主KWが1つに絞れる（第2-1節） |
| ハブへのリンク | 冒頭または末尾で「全体像はこちら」 |
| 次のスポークへ | ジャーニーの次段階への導管 |
| 更新しやすさ | 制度・数値が変わる部分はH2単位で更新可能（第11-3節） |

スポーク同士が競合（カニバリ）しないよう、主KWの重複をチェックします。第11-4節のカニバリ診断を、新規スポーク追加前のルーティンに組み込みます。

## クラスター設計の手順

> この節の要点：テーマ領域→ジャーニーマッピング→ハブ選定→スポーク列挙→ギャップ特定→リンク設計の6ステップ。

整備計画を書く順序と同じ流れです。

```
Step 1：テーマ領域を決める
  ペルソナ（第2章）× ビジネス目標 × 既存記事の棚卸し
        ↓
Step 2：ジャーニー段階をマッピング
  認知→検討→決定→行動（第2-6節）に、問いを配置
        ↓
Step 3：ハブ候補を1つ選ぶ
  最も広い問い、または既存の表示数が多い記事
        ↓
Step 4：スポークを列挙
  各段階の問いを1記事1問いで割り当て
        ↓
Step 5：ギャップを特定
  計画にあるが未執筆 / 既存だが役割不明 / カニバリ
        ↓
Step 6：内部リンク設計
  ハブ↔スポーク、スポーク↔スポーク（第5-5節）
```

## 既存記事からクラスターを組み立てる

> この節の要点：新規サイトでなく既存記事がある場合、Step 1の棚卸しが出発点。主KW重複・表示数・孤立・薄い記事を洗い出す。

新規サイトではなく、既に記事があるサイトでは、Step 1の棚卸しが出発点です。

| 棚卸しの観点 | やること |
|---|---|
| 主KWの重複 | 同じ問いに答える記事をリストアップ |
| 表示数・外門の通過 | 第6章のデータでハブ候補を特定 |
| リンクの孤立 | どこからもリンクされない記事（第5-5節） |
| 薄い記事 | Must未達の短い記事（統合候補、第11-1節） |

```
棚卸しシート（例：副業クラスター）

| URL | 主KW | 文字数 | 表示(28日) | 役割案 | メモ |
|---|---|---|---|---|---|
| /side-job-guide/ | 副業 始め方 | 3,500 | 8,200 | ハブ | 既存 |
| /side-job-rules/ | 副業 就業規則 | 1,200 | 1,400 | スポーク | リンク追加要 |
| /side-job-tips/ | 副業 コツ | 800 | 320 | 統合候補 | ハブに吸収 |
```

## 複数クラスターのサイト設計

> この節の要点：1サイトに複数クラスターがある場合、ジャーニーが自然につながる場合のみクラスター間リンクを張る。

1サイトに複数のテーマ領域がある場合、クラスターは複数存在します。

```
サイト全体
  ├── クラスターA：副業
  │     ハブ + スポーク群
  ├── クラスターB：確定申告
  │     ハブ + スポーク群
  └── クラスターC：在宅ワーク
        ハブ + スポーク群
```

クラスター間のリンクは、ジャーニーが自然につながる場合のみ張ります。例：副業クラスターの「確定申告」スポークから、確定申告クラスターのハブへ。無関係なクラスター間のリンクは、物流を濁らせます（第5-5節）。

寿司職人が複数のコース（昼・夜・宴会）を持つように、クラスターごとに献立（記事群）を設計し、サイト全体のメニュー表（ナビゲーション・カテゴリ）で読者を案内します。

---

### ポイント

- クラスター＝ハブ（概観）＋スポーク（詳細）＋双方向リンク
- ハブはMust/Should/Could/Won't（第3-6節）で削ぎ落とし、詳細はスポークへ
- スポークは1記事1問い。カニバリチェックを新規前に実施
- 既存サイトは棚卸しから。統合・役割変更・リンク追加が初期タスク
- 第2章ジャーニー、第5章物流、第11章統合と接続

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| すべてハブにしようとする | どれも薄い、カニバリ | 1クラスター1ハブ |
| スポークにハブの内容をコピー | 重複・カニバリ | ハブは概要＋リンクのみ |
| リンクを公開後に忘れる | 孤立ページ、物流断絶 | 執筆時にリンク設計（第5-5節） |
| クラスター境界が曖昧 | 読者・クローラーが迷子 | テーマ領域を1文で定義 |
