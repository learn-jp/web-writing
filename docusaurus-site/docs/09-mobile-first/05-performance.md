# 9-5 読み込み速度と文章量のバランス

返球が届く前に戻ってしまったように見えても、文章量とメディアの載せ方はライターが関与できる領域です。Core Web Vitalsはエンジニアとデザインの領域ですが、必要な分だけ載せ、読み込みの重さとして設計すれば、検索・SNS・AI引用のどの入口から来ても、本文に辿り着けます。

## 表示速度も、返球の「物流」の一部

> この節の要点：Core Web Vitalsは主にエンジニアとデザインの領域だが、文字数・画像・埋め込みはページの重さに直結する。不要な荷物を降ろすように、読み込みの重さを意識して設計する。

第5章（[Web最適化（検索・SNS・AI引用）](../05-seo-basics/)）で、届け方（物流）を学びました。Core Web Vitals（表示速度の指標）は、主にエンジニアとデザインの領域です。しかし、あなたが記事に載せる文字数、画像の数、埋め込み（動画、地図、SNSウィジェット）は、ページの重さに直結します。検索経由でも、SNSからタップしても、AI引用から辿ってきても：いずれも、表示が遅ければ自分は本文に辿り着く前に戻ります。

自動車整備士が走行性能を上げるために、不要な荷物を降ろすように、モバイル向けのあなたの物語は「読み込みの重さ」を意識して設計します。

| ライターが関与できる要素 | 重さへの影響 |
|---|---|
| 文章量（総文字数） | HTMLサイズ、レンダリング時間 |
| 画像の数と説明 | 画像ファイル、altの有無（第10章） |
| 埋め込み（動画、SNS等） | 外部スクリプト、追加リクエスト |
| 表・リストの過剰なネスト | DOMの複雑化 |

---

## 文章量の目安：必要な分だけ、削ぎ落とした分だけ

> この節の要点：モバイルファーストは「短く書け」ではない。Mustを満たす最小量を書き、それ以上は別記事・折りたたみ・リンクへ逃がす。

モバイルファーストは「短く書け」という意味ではありません。第3章の「優先順位づけと削ぎ落とし」を、読み込みと読了時間の両方で考えることです。

### 問いに答えるのに必要な最小量を書く

寿司職人が握りに載せるネタは、シャリとのバランスで決まります。載せすぎれば握りが崩れ、少なければ客が物足りなく感じます。記事も、Must（約束）を果たすのに必要な情報量が、正しい量です。

```
判断の順序
1. この問いに答えるのに、何がMustか（第2章）
2. Mustを満たすのに、各H2は何字必要か
3. それ以上は、別記事・折りたたみ・リンクへ逃がす
```

8000字の記事が常に正しいわけではありません。スマホで通勤中に読む500字のチェックリスト記事の方が、問いに合っている場合もあります。

### 長文記事のモバイル向け分割

1つの問いに8000字必要な場合、目次・アンカーリンク・H2の明確な関所で「部分読了」を可能にします（第9-2節）。全文を一度に読ませるのではなく、関所ごとに完結した返球を設計します。

---

## 画像とメディア：載せる理由を一行で言えるか

> この節の要点：画像は理解を助けるが、ファイルサイズは読み込みを遅くする。載せる前に、本文だけで答えられるか・altを書けるか・装飾目的でないかを確認する。

画像は理解を助けますが、ファイルサイズは読み込みを遅くします。載せる前に、次を確認してください。

```
□ この画像がなくても、本文だけで問いに答えられるか
□ 代替テキスト（alt）を書けるか（第10章）
□ スマホ幅でも内容が読める解像度・トリミングか
□ 装飾目的だけの画像はないか
```

「なんとなく挿入」している画像は、整備士が理由なく重量物を積むのと同じ。削るか、本文で言い換えます。

---

## 埋め込みメディアの抑制

> この節の要点：動画・地図・SNSの埋め込みはページを大幅に重くする。Mustでない限りリンクに置き換え、動画が不可欠な場合はサムネイル＋リンク形式を検討する。

動画、地図、SNSのタイムライン埋め込みは、ページを大幅に重くします。

| 埋め込み | モバイル向けの代替 |
|---|---|
| 動画 | リンク「動画で手順を確認（3分）」＋本文で要点 |
| 地図 | 住所テキスト＋「地図アプリで開く」リンク |
| SNSタイムライン | スクリーンショット1枚＋出典、またはリンクのみ |

動画がMustの場合（手順の視覚的説明が不可欠）は、サムネイル＋リンク形式にし、自動再生埋め込みを避ける選択肢をエンジニアと相談します。

---

## 第6章の第2の返球と速度

> この節の要点：クリックはあるが一ページだけ見て去る傾向が強い記事は、外門と玄関のズレだけでなく、表示の遅さが原因の場合もある。精密検査で「速度」も含めて疑う。

公開後、一ページだけ見て去る割合が高く、読み続けてくれた時間が極端に短い記事（第6章）は、問いと答えのズレだけでなく、表示速度が原因の場合もあります。

```
症状：クリックはあるが、一ページだけ見て去る傾向が強い、置いてくれた時間が数秒
疑う原因：
  ・外門と玄関のズレ（第4章・第9-3節）
  ・表示が遅く、本文を読む前に戻る（本章）
  ・ファーストビューに答えがない（第9-3節）
```

精密検査（第6章）で玄関で引き返す傾向を見たとき、レイヤーを「速度」も含めて疑う。PageSpeed Insights等の結果はエンジニアと共有し、ライター側で削れる要素（画像、埋め込み、冗長な前置き）を提案します。

## 公開前の「軽さ」チェックリスト

> この節の要点：総文字数・画像・埋め込み・スマホでの体感速度を、納車前の空車重量確認のように公開前に点検する。

```
□ 総文字数は、Mustを満たすのに過不足ないか
□ 画像は各枚に存在理由とaltがあるか
□ 埋め込みはMustでない限りリンクに置き換えたか
□ スマホで実際に開き、体感ですぐに本文が見えるか（体感）
□ 表・リストが過剰にネストしていないか
```

整備士が納車前に空車重量を確認するように、公開前の「軽さ」確認は、スマホで読む自分への礼儀です。

---

### ポイント

- 表示速度は物流（第5章 Web最適化）の延長。入り口を問わず、ライターは文字量・画像・埋め込みで関与
- 必要な最小量を書く。長文は関所分割で部分読了を可能に
- 画像・埋め込みは理由を一行で説明できるものだけ
- 玄関で引き返す原因に「遅さ」も含めて疑う（第6章と連動）

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| 文字数を KPI にする | 冗長な前置きが増える | Must基準で量を決める |
| 画像を装飾で大量挿入 | 読み込みが遅い | 本文で足りるなら削る |
| 動画を自動埋め込み | モバイルで重い | リンク＋本文で要点 |
| 速度はエンジニアだけの問題 | ライター側の改善余地を見逃す | 文字量・メディアを見直す |
