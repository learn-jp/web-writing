# 9-3 ファーストビューの設計

記事を開いて、スクロールする前の一瞬で「これ、自分の問いの答えか？」と判断されます。ここで戻ってしまっても、あなたの努力が足りないわけではありません。外門（title・meta）と玄関（H1・リード）の設計を整えれば、自分なら本文へ進みます。タイトル、リード、最初の見出し。ここで引き返すかどうかが決まります。

## ファーストビュー＝スクロール前の玄関全体

> この節の要点：H1、リード文、最初のH2の冒頭が、スクロールなしで見える範囲に収まっているか。それがファーストビューの設計である。

第4章（[見出しとリード文](../04-headlines-leads/)）で、入口を「玄関」と呼びました。H1、リード文、最初のH2の冒頭。これらが、スクロールなしで見える範囲に収まっているか。それがファーストビューの設計です。

スマホでは、ファーストビューに入る要素がPCより少なくなります。

| 要素 | スマホでの目安 | 役割 |
|---|---|---|
| H1（記事タイトル） | 1〜2行 | 問いへのラベル |
| リード文 | 2〜3文（80〜120字程度） | 防波堤、答えの予告 |
| 目次・リード直後の要点 | あれば3行以内 | スキャン用の地図 |
| 最初のH2見出し | 1行 | 次の関所の予告 |

自動車整備士が車をピットに入れた瞬間、メーターと異音を最初に確認するように、自分もファーストビューで「この返球、受け取る価値があるか」を判断します。

---

## スマホの「一瞬」は、第4章の「玄関で決まる一瞬」と同じ

> この節の要点：第4章の「消滅と競争する玄関で決まる一瞬」は、スマホでは画面量の少なさ・中断されやすい文脈・親指一本のスクロール判断により、圧力がより強くなる。

第4章で学んだ「消滅と競争する玄関で決まる一瞬」は、デバイスを問わず成立します。ただしスマホでは、

- 1画面に見える文字量が少ない（第2章）
- 中断されやすい文脈（通勤、移動中）
- 親指一本でのスクロール判断

という条件が重なり、一瞬の圧力はより強くなります。

寿司職人が客の前に最初の一貫を出すタイミングと、あなたがファーストビューに答えの予告を置くタイミングは同じです。最初の一口（一行）で「この店（記事）、期待できる」と思わせる。

---

## ファーストビューに置くべき三要素

> この節の要点：問いへの適合宣言、答えの予告（結論の核）、次の関所への誘導。ファーストビューに置く三要素。

### 要素1：問いへの適合宣言

リードの1文目で、「誰の、どんな問いに答えるか」を明示します。第2章のペルソナとMust（約束）を、1文に圧縮します。

```
例（副業ハウトゥ）
「会社員の健太さんが、就業規則を確認しながら副業を始めるための、最初の3ステップをまとめました。」
```

### 要素2：答えの予告（結論の核）

第4章（[4-4 結論ファースト](../04-headlines-leads/04-conclusion-first.md)）の技法を、リード2〜3文目に配置します。詳細は本文へ。予告だけで「読む価値」を示します。

```
例
「結論から言うと、副業を始める前に就業規則の確認、届け出の要否、時間の確保の順で進めるのが安全です。以下、各ステップを解説します。」
```

### 要素3：次の関所への誘導

最初のH2見出しが、ファーストビューに少し見える状態が理想です。「この先、何が書いてあるか」が見えると、スクロールの動機になります。

---

## ファーストビューで避けるべき配置

> この節の要点：長い著者紹介、関連記事の羅列、長い目次はファーストビューを食いつぶす「玄関の荷物」。答えが見える前にスクロールを要求しない。

| 避ける配置 | 理由 | 代替 |
|---|---|---|
| リード前の長い前置き | 答えが見えない | 前置きは削るか本文へ |
| ファーストビュー内の横長バナー | 文字領域を圧迫 | 本文後半またはサイド相当へ |
| 目次が10行以上 | スクロール前に何も読めない | 折りたたみ、または3項目以内 |
| H1とリードの重複 | 同じ情報の二度読み | H1はラベル、リードは予告 |

---

## ファーストビューの設計手順

> この節の要点：スマホプレビューでスクロールせず見える範囲を確認し、問いへの適合・答えの予告・最初のH2・不要要素の四つをチェックする。

執筆の終盤、または公開前に、次の手順で確認します。

```
1. スマホプレビューを開く
2. スクロールせず、見える範囲をスクリーンショット
3. チェック：
   □ 問いへの適合が1文目でわかるか
   □ 答えの予告（結論の核）があるか
   □ 最初のH2が少し見えるか
   □ 不要な要素（バナー・長目次）がないか
4. 足りなければリードを書き直す（H1は第5章 Web最適化（検索・SNS・AI引用）の物流と整合）
```

整備士が最小ピットでエンジンルームが一望できるように配置するように、ファーストビューは「答えの所在」が一望できる状態を目指します。

---

## 入り口（検索・SNS・AI引用）とファーストビューの整合

> この節の要点：検索結果・SNSプレビュー・AI引用スニペットは、いずれも「入り口の外門」。外門で約束した答えがファーストビューで予告されているか。モバイルの玄関設計は物流のラベルと一体。

自分が検索結果から来ることが多いですが、SNSのリンクプレビューや、Gemini・ChatGPTなどのAI回答に引用されたURLから来ることも増えています。いずれも、title・meta description（またはOGP）が最初に見える「外門」です。第5章 Web最適化（検索・SNS・AI引用）で設計したラベルと、H1・リードの内容がズレていると、クリック後の玄関で自分なら引き返す（第6章）が起きます。

```
入り口（外門）→ クリック → ファーストビュー（玄関）→ 本文（導管）
  検索 / SNS / AI引用     H1 + リード           H2以降
     title/meta
```

外門で約束した答えが、ファーストビューで予告されているか。モバイルファーストの玄関設計は、入り口を問わず物流のラベルと一体です。

---

### ポイント

- ファーストビュー＝スクロール前の玄関（H1＋リード＋最初のH2）
- 問いへの適合、答えの予告、次関所の誘導の三要素
- 長い前置き・目次・バナーはファーストビューを圧迫する
- title・meta（第5章 Web最適化）とH1・リードの整合を確認。SNS・AI引用でも同じ約束が伝わるか

### よくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| リードが背景説明のみ | 答えの予告がない | 結論の核を2文目以内に |
| H1とリードが同じ内容 | 情報の無駄 | H1は短く、リードで予告 |
| ファーストビューに目次だけ | 本文に到達しない | 目次を折りたたみ |
| PCでしかファーストビュー確認 | スマホで要素が切れる | スマホスクリーンショットで確認 |
