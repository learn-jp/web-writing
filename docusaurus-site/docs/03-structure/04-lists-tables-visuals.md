# 3-4 リスト・表・図版の使い分け

手順や比較項目を、長い段落で書いていませんか。リスト・表・図版は装飾ではなく、情報の導管における「分岐・合流・並列処理」を設計する構造要素です。並列情報を正しい構造に分岐させ、読者のワーキングメモリへの負荷を減らします。

## なぜ「並列情報」は導管を分岐させるのか

> この節の要点：手順・比較・条件分岐など並列情報は段落ではなくリスト・表で構造化する。導管の分岐と合流を、読者の脳に代わって整理する。

段落は「直列」の情報流れに向いています。一方、次のような情報は「並列」です。

- 手順が3つ以上続く（Do型）
- 選択肢を比較する（Buy型）
- 条件ごとに答えが分かれる（Know型）

並列情報を段落で書くと、「1本の導管に流れを無理やり合流」させることになります。読者は「1つ目、2つ目、3つ目…」と数えながら読み、「ワーキングメモリ」に負荷がかかります。

> 「並列情報には、並列の構造（リスト・表）を使う。」  
> 「それは、導管の分岐と合流を、読者の脳に代わって整理することである。」

---

## リスト、順序と並列の設計

> この節の要点：箇条書き（ul）は順序なし並列、番号付きリスト（ol）は順序あり直列。Do型は番号リストが定番。

### 箇条書き（ul）、順序が不要な並列

「使う場面」：条件の列挙、特徴の並列、注意点の集合

```html
<h2>始める前に確認すること</h2>
<ul>
  <li>就業規則の兼業・競業条項</li>
  <li>確定申告の概要</li>
  <li>本業との時間配分</li>
</ul>
```

「ブラウザでの表示結果（見た目）」：

- 各項目が箇条書きの記号（・）付きで縦に並び、一覧性が高い
- 順序に意味がない項目が、同じ粒度で並んで見える
- スマホでも1項目1行で読みやすい

「設計の原則」：

- 各項目は「同じ文法・同じ抽象度」で揃える（並びの論理。第3-2節）
- 1項目1行。1項目に複数の論点を入れない
- 5〜7項目を超える場合は、H3で「グループ分け」する

### 番号付きリスト（ol）、順序がある直列

「使う場面」：手順（Do型）、段階的なプロセス、優先順位

```html
<h2>今週末に登録まで進む手順</h2>
<ol>
  <li>就業規則を確認する</li>
  <li>副業の種類を1つ選ぶ</li>
  <li>アカウントを登録する</li>
  <li>最初の1件に応募する</li>
</ol>
```

「ブラウザでの表示結果（見た目）」：

- 1、2、3……と番号が付き、手順の順序が一目でわかる
- Do型の読者が、必要なステップだけジャンプして読める
- 各ステップが独立した行になり、実行可能性が伝わる

「設計の原則」：

- 各ステップは「動詞で始める」（実行可能性）
- 1ステップ＝1アクション。複合動作は分割
- ステップ間に「依存関係」がある場合、番号リストが必須

| 情報の性質 | 使うリスト |
|---|---|
| 順序なし・同等の項目 | 箇条書き（ul） |
| 順序あり・手順 | 番号付き（ol） |
| 階層がある並列 | ネストしたリスト（深くしすぎない） |

## 表、比較とマトリクスの設計

> この節の要点：表は2次元以上の情報を合流点として整理する。Buy型の比較に有効だが、スマホでは本文でも要点を補足する。

「使う場面」：Buy型の比較、条件×結果のマトリクス、仕様の対照

表は、「2次元以上の情報」を、導管上の「合流点」として整理します。

```html
<h2>初心者向け副業の比較</h2>
<table>
  <tr><th>副業の種類</th><th>初期費用</th><th>週あたり時間</th><th>在宅可否</th></tr>
  <tr><td>ライティング</td><td>0円</td><td>2〜5時間</td><td>○</td></tr>
  <tr><td>動画編集</td><td>0〜1万円</td><td>5〜10時間</td><td>○</td></tr>
  <tr><td>ハンドメイド販売</td><td>材料費</td><td>可変</td><td>△</td></tr>
</table>
```

「ブラウザでの表示結果（見た目）」：

- 行と列の見出しで、複数の比較軸が一度に並ぶ
- Buy型の読者が、気になる列だけスキャンできる
- スマホでは横スクロールになることが多い（要点は本文でも補足する）

「設計の原則」：

- 「1表1テーマ」。複数の比較軸を1表に詰め込みすぎない
- 行・列の見出しは「内容がわかる文言」に（「項目A」は不可）
- スマホでは表が横スクロールになることが多い。「要点は本文でも補足」する（第2章）
- 表だけ読んでも、判断材料が得られるようにする
- ChatGPTやGeminiなどのAIは、表やリストから数値・手順・比較結果を抽出しやすい。並列情報を構造化しておくことは、AI経由の引用でも読者への正確な返球につながる

## 図版、視覚的な関所

> この節の要点：フローチャート・概念図・スクリーンショットは言語より早く通過できる関所。altで全読者に標識を設計する。

フローチャート、概念図、スクリーンショットは、「言語より早く通過できる関所」です。

| 図の種類 | 導管上の役割 | 例 |
|---|---|---|
| フローチャート | 分岐と合流の可視化 | 判断フロー「バレる？→規約確認→…」 |
| 概念図 | 全体構造の俯瞰 | PREP・逆ピラミッドの模式図 |
| スクリーンショット | Do型の具体的手がかり | 登録画面の操作箇所 |
| グラフ | 数値の比較 | 料金プランの違い |

第1章で、画像には「代替テキスト（alt）」が必要だと述べました。図版は、「見えない読者への標識」も設計します。altには「何がわかる図か」を書く。それも導管設計の一部です。

自動車整備士が配線図で故障箇所を特定するように、図版は言語では伝えにくい構造を一瞬で示します。

---

## 使い分けの判断フロー

> この節の要点：情報が直列か並列かを見極め、順序・対照・視覚化の必要性に応じてリスト・表・図版を選ぶ。

```
情報は並列か、直列か？
  ├ 直列 → 段落（第3-3節）
  └ 並列
       ├ 順序あり → 番号付きリスト
       ├ 順序なし → 箇条書き
       ├ 2次元以上の対照 → 表
       └ 空間的・手順的に視覚化が有効 → 図版
```

「Do型」の記事では、番号リスト＋スクリーンショットの組み合わせが定番です。「Buy型」では表＋Pros/Consリスト。「Know型」では、概念図＋箇条書きの要約。

---

## リスト・表の「構造の美学」

> この節の要点：リストに逃げすぎない。前後に導入・締めの段落を置き、分岐導管を幹線に接続する。

第3-6節で詳述しますが、ここで一点だけ。

「リストに逃げすぎない。」 すべてを箇条書きにすると、記事が「断片の集合」になり、論理の勾配（Reason）が失われます。リストの前後には、「なぜこのリストが必要か」を1文で書く。導入と締めの段落が、分岐導管を幹線に接続します。

```
✓ 導入段落：「確認すべき項目は次の3つです。」
  → リスト
  → 締め段落：「以上を確認してから、種類選びに進みましょう。」

✗ いきなりリストだけ
```

寿司職人が握る前に下準備を整えるように、リストの前後の導入・締めは「おもてなし」の設計です。

---

### リスト・表・図版のポイント

- 並列情報は段落ではなく、「リスト・表」で構造化する
- 箇条書き＝順序なし並列、番号リスト＝順序あり直列
- 表は比較・マトリクス。スマホでは本文でも要点を補足
- 図版は視覚的な関所。altで全読者に標識を
- リスト・表はAI（ChatGPT・Gemini等）が引用・要約しやすい構造でもある
- リストの前後に導入・締めを置き、幹線に接続する

### リスト・表・図版でよくある間違い

| 間違い | 問題 | 改善の方向 |
|---|---|---|
| 長い段落をリストに分割しない | 認知負荷が高い | 3項目以上の並列はリスト化 |
| 表がスマホで読めない | 情報が届かない | リスト化または要点を本文に |
| リスト項目の抽象度がバラバラ | 並びの論理が崩れる | 同じ文法・粒度に揃える |
| 図にaltがない | 画像に依存する読者に届かない | 内容が伝わるaltを書く |
