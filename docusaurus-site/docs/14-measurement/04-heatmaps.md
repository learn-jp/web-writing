# 14-4 ヒートマップとユーザー行動分析

公開後、自分が読者として記事を読み返したとき、どこでスクロールを止め、どこで戻ったか。それを思い出す助けがヒートマップです。Search ConsoleとAnalyticsでは見えない「関所での詰まり」を、自分の体験と照らし合わせて確認し、第11章の部分リライトへつなげます。

## ヒートマップとは何か（初心者向け）

> この節の要点：ヒートマップは、自分がどこで足を止め、どこで戻ったかを思い出すための観察メモである。読み返しの記憶を、色で補強する。

ページ上のどこに目を止め、どこをタップし、どこまでスクロールしたかを、色の濃淡で可視化するツールです。

| 色 | 意味 |
|---|---|
| 赤・オレンジ（濃い） | 多くの人（自分を含む）が目を止めた・タップした |
| 黄・緑（中間） | 一部が見た |
| 青（薄い） | ほとんど見られなかった |

初心者向けに言い換えると、ヒートマップは「自分が読者として読み返したとき、どこで戻ったか」を、記憶の補助として色で映し出す工具です。

公開後にスマホで自分の記事を開き直し、「ここでスクロールが止まった」「このH2の前で戻った」と感じた場所があるはずです。ヒートマップは、その体験が自分だけの感覚ではなかったかを確かめる助けになります。

自動車整備士が走行後の異音を、もう一度試走して再現するように、ヒートマップは「読者としての自分」の体験を、画面の上で再確認する工具です。

---

## 3種類のヒートマップ

> この節の要点：クリック・スクロール・注意の3種類を使い分ける。スクロールマップは、自分がどこで戻ったかを思い出す最強の助けである。

ツールによって名称は異なりますが、実務で使うのは主に3種類です。

| 種類 | 何を見るか | Webライティングでの用途 |
|---|---|---|
| クリックマップ | どこがタップされたか | CTA・リンクの設計（第9-4節） |
| スクロールマップ | どこまで読まれたか | 関所（H2）前後で自分が戻る場所 |
| ムーブマップ（注意マップ） | どこに目が止まったか | 見出し・画像・表の注目度 |

### クリックマップの読み方

自分が読者として読み返したとき、「ここを押したい」と感じた場所にタップが集中しているかを確かめます。CTAボタンにタップがないなら、視認性か文言の問題（第9章）を疑います。

```
タップ集中：目立つリンク・比較表・目次
タップゼロ：グレーのテキストリンク・小さなボタン
誤タップ多：画像・装飾がリンクと誤認されている
```

### スクロールマップの読み方

スクロールマップは、自分がどこで戻ったかを思い出す最強の助けです。第6-2節の「特定H2で戻る」予兆を、読み返しの記憶と照らして確認できます。

```
100%  ━━━━━━━━━━  全員が到達（リード）
 75%  ━━━━━━━░░░  H2-1前で25%が戻る → リード・H2-1見出しを疑う
 50%  ━━━━━░░░░░  H2-2前でさらに戻る → H2-2の関所
 25%  ━━░░░░░░░░  結論まで届いていない
```

GA4のスクロールイベントだけでもおおまかな把握は可能です。より細かく、自分の読み返し体験と照らしたい場合に、ヒートマップツールを追加します。

## 第6章・第11章との接続

> この節の要点：GSC・GA4で異常を掴み、ヒートマップで「読者としての自分」が戻る関所を特定し、第11章の部分リライトへ接続する。診断機→内視鏡→部品交換の流れである。

ヒートマップは、精密検査とリライトの「どこを直すか」を、自分の読み返し体験と照らして特定する補助です。

```
第6章 精密検査
  └ GSC：クエリズレを発見
  └ GA4：玄関で引き返す・読み続け時間で防波堤を疑う
        ↓
第14章 ヒートマップ
  └ スクロール：どのH2で自分が戻るか可視化
  └ クリック：CTAが自分の指に届くか
        ↓
第11章 リライト
  └ 部分リライト：特定H2・リードのみ修正
  └ 再試運転：28日後にスクロール深度を再確認
```

整備士が診断機（GSC・GA4）で異常を掴み、内視鏡（ヒートマップ）で関所を特定し、部品交換（部分リライト）する流れです。

## いつヒートマップを使うか

> この節の要点：異常が疑われる記事に限定する。表示50未満や外門だけの問題には使わない。月次ルーティンが先である。

| 使う条件 | 理由 |
|---|---|
| 表示500以上・玄関で引き返す傾向が同タイプより強い | データ量が分析に十分 |
| GA4で「特定H2で戻る」が疑われる | 関所の特定が必要 |
| CTA・CV改善が四半期KPI | クリックマップが有効 |
| 全面リライト前の現状把握 | オーバーホール前の分解図 |

| 使わない条件 | 理由 |
|---|---|
| 表示50未満 | サンプル不足で誤判断 |
| 外門だけが問題（外門の通過が弱い） | title修正が先（第5-3節） |
| 月次ルーティンが未習慣化 | まず第6-6節を固定 |

寿司職人が毎日全ネタを温度計で測らないように、ヒートマップは「異常が疑われる記事」に限定します。まず自分が読者として読み返し、戻る場所を感覚で掴んでから、計器で確かめる順番が自然です。

## 主なツール（参考）

> この節の要点：無料のClarity＋GA4スクロールで本章の学びは実践できる。高価な工具より第6章の点検段取りが重要である。

| ツール | 特徴 | 備考 |
|---|---|---|
| Microsoft Clarity | 無料、スクロール・クリック | 小規模サイト向け |
| Hotjar | ヒートマップ＋セッション録画 | 有料プランあり |
| GA4 スクロールイベント | Analytics内蔵 | ヒートマップより粗い |
| ブラウザ拡張（簡易） | 手軽 | 本格分析には不向き |

高価な工具より、第6章の点検段取りが重要です。無料のClarity＋GA4スクロールで、本章の学びは実践できます。

## セッション録画との併用

> この節の要点：録画は仮説生成に使い、改善判断は集計データで行う。1人のセッションで全面リライトを決めない。

一部のツールは、個別セッションの録画（リプレイ）も提供します。マウス移動・スクロール・タップの動きを動画で見られます。

| メリット | 注意 |
|---|---|
| 「なぜここで戻るか」の仮説が増える | 他人を覗く道具ではなく、自分の読み返し体験の補助として使う |
| フォーム・UIの問題も発見 | 文章以外の原因も見える |

録画は仮説生成に使い、改善判断は集計データ（スクロール率・外門の通過）で行います。1人のセッションで全面リライトを決めないでください。

---

## ヒートマップから改善アクションへ

> この節の要点：ヒートマップのサインをレイヤーとアクションに対応づける。改善後は28日後に再取得し、スクロール深度の変化を確認する。

| ヒートマップのサイン | 疑うレイヤー | アクション例 |
|---|---|---|
| リード直後にスクロール急減 | 防波堤 | リード短縮・問い宣言（第4章） |
| H2-2前で急減 | 関所 | H2見出し変更・段落分割（第3章） |
| CTAにタップゼロ | 行動設計 | ボタン文言・位置（第9-4節） |
| 目次・リンクに集中 | 正常 | 内部リンク強化（第5-5節） |
| 画像に誤タップ | UI | alt・リンク設計（第10-3節） |

改善後は、第11章の再試運転と同様、28日後にヒートマップを再取得し、自分が読者として読み返したときのスクロール深度の変化を確認します。

---

## よくある間違い

> この節の要点：ヒートマップだけで判断せずGSC・GA4と束ねる。全記事にかけず、見て終わりにせず改善ログに1行書く。

| 間違い | 改善 |
|---|---|
| ヒートマップだけで判断 | GSC・GA4と束ねる（第6-3節） |
| 全記事にかける | 異常記事・重点記事に限定 |
| 1セッションで判断 | 集計データで判断 |
| 見て終わり | 改善ログに1行書く（第6-6節） |
| 文章以外の問題を無視 | UI・速度も第9-5節で確認 |
| 他人の行動を覗く道具にする | まず自分が読者として読み返し、計器で確かめる |
